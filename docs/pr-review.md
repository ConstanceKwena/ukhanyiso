# Code review of work-branch (iteration 2)

Reviewed: the commits on `work-branch` up to `06c7e6b Add APS calculator and unit tests`, as uploaded on 2026-10-20.
Not reviewed: the GitHub pull-request pages themselves (comments, approvals, who opened what). I only had the code. If a PR is open, paste its link or diff and I'll review it the same way.

Severity: **High** = breaks the build, hides failures or leaks data. **Medium** = confusing or risky, fix soon. **Low** = tidy-up.

## High

| # | Finding | Evidence | Fix |
|---|---|---|---|
| H1 | **The security tests never run.** `SecurityTestSuites` does not match Maven's default test names (`*Test`, `*Tests`, `Test*`, `*TestCase`), so `mvn test` skips it. | `target/surefire-reports/` has a report only for `SourceVerificationTest`; the compiled `SecurityTestSuites.class` is there but has no report. | Rename the class to `SecurityTests` (file and class). Then read H4 before expecting it to pass. |
| H2 | **`schema.sql` / `data.sql` probably fail on H2.** They were written for SQLite: `TEXT PRIMARY KEY` (H2 treats TEXT as a large object), `req_id INTEGER PRIMARY KEY` with no auto-numbering while `data.sql` leaves `req_id` out, and `BEGIN;` / `COMMIT;` lines. | Reading the files. I could not run H2 in my environment, so this is a strong suspicion, not a confirmed failure. | My patch replaces both files with H2-safe versions (`VARCHAR`, `GENERATED BY DEFAULT AS IDENTITY`, no BEGIN/COMMIT). `CatalogRepositoryTest` loads them on the first `mvn test`. |
| H3 | **Stale duplicate files are still tracked in git.** `src/Matching/` holds old copies of `MatchingController`, `MatchingRecord`, `MatchingRepository`, `MatchingService`; the real ones are under `src/main/java/com/ukhanyiso/matching/`. In the uploaded copy the old ones are deleted on disk but the deletion is not committed. | `git ls-files` lists `src/Matching/*.java`; `git status` shows ` D src/Matching/...`. | `git rm -r src/Matching` and commit. |
| H4 | **The security tests do not test what their names say.** "Role access" posts a request and expects 200: the app has no login or roles. The SQL-injection test only checks nothing throws, not that the table survived. The "spam" test expects HTTP 500 for blank input; blank input is the caller's mistake and should be 400. I also expect that test to error rather than return 500, because MockMvc rethrows an unhandled `IllegalArgumentException`. | `SecurityTestSuites.java`. The second point is my expectation from how MockMvc works; it has never run, so run it to see. | Add a handler that turns `IllegalArgumentException` into 400 for `/api/matching/**`, change the test to expect 400, and record "access control: NOT IMPLEMENTED (no accounts)" in Kwena's checklist. The new `MatchApiTest` shows the style. |
| H5 | **`POST /api/matching/process` is open to anyone and writes to the database.** It saves any string of any length as a new row (the column is unique), so a script can fill the database. The marks flow does not need it. | `MatchingController`, `MatchingService`, `MatchingRecord`. | Stop using it once `/api/match` is wired to the front end, then remove it (and `MatchingRecord`). Until then, cap the length and add the same size filter. |
